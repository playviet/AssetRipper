## 1. Unity version parsing and detection — **fine**

The version is not parsed from a gate-guarded table; it is read out of the IL2CPP metadata and
carried through unchanged.

- `Source/AssetRipper.Import/Structure/Assembly/Managers/Il2CppManager.cs` logs it — the log line
  `During Il2Cpp initialization, found Unity version: 6000.0.66f2` is the proof it round-tripped through
  `UnityVersion.Parse` with no clamping.
- The project version is then `GameBundle.GetMaxUnityVersion()`:
  `Source/AssetRipper.Assets/Bundles/GameBundle.cs:89-91` —
  `FetchAssetCollections().Select(t => t.Version).Append(UnityVersion.MinVersion).Max()`.
  `Max()` has no ceiling, so 6000.x wins as it should.
- `Source/AssetRipper.Processing/GameData.cs:22` passes that into `CoreConfiguration.Version`
  (`Source/AssetRipper.Import/Configuration/CoreConfiguration.cs:39,52`).

`UnityVersion` stores major as a plain number, so Unity 6 is major `6000` and sorts above `2023`.
Every comparison in `Source/` that could have been a ceiling is checked in item 5 and in the
`AssetRipper.Import` sweep below.

**Verify:**
```sh
grep -n "found Unity version" "$LOG"
grep -n "Game files have these Unity versions" "$LOG"
grep -n "Exporting to Unity version" "$LOG"
```
Expect `6000.0.66f2` in all three. If the second line lists several versions, the *max* is what
everything downstream uses — a stray older collection cannot drag the project version down, but a
stray **newer** one would raise it.

## 2-3. The class/asset layout database — **fine**

The layout database is the `AssetRipper.SourceGenerated` NuGet package, pinned at
`Source/AssetRipper.SourceGenerated.Extensions/AssetRipper.SourceGenerated.Extensions.csproj:16`
to **version 1.4.0** (`~/.nuget/packages/assetripper.sourcegenerated/1.4.0/lib/net10.0/AssetRipper.SourceGenerated.dll`,
65 MB). It is generated by `Source/AssetRipper.AssemblyDumper/`.

**It has an exact entry for 6000.0.66.** Layout classes are named with the version at which the layout
changed:

```sh
strings -n 6 ~/.nuget/packages/assetripper.sourcegenerated/1.4.0/lib/net10.0/AssetRipper.SourceGenerated.dll \
  | grep -oE '_6000_[0-9]+_[0-9]+' | sort -u
```
`_6000_0_66` is present, and the DB runs to `_6000_7_0` — well past the target. 220 distinct version
breakpoints in total. **The DB is not the constraint here.**

**What happens with no exact entry: nearest *lower* match, never a throw.**
- Per-class version dispatch is a descending chain of `UnityVersion.GreaterThanOrEquals`, emitted by
  `Source/AssetRipper.AssemblyDumper/Passes/Pass940_MakeAssetFactory.cs:41-42` and
  `ImplementNormalCreationMethod` (`:269-278`). A version above every breakpoint takes the newest one.
- Unknown **ClassID** (not version) falls off the switch and returns null:
  `Pass940_MakeAssetFactory.cs:154-156` (`defaultNop` → `Ldnull` → `Ret`).
- That null is then handled in `Source/AssetRipper.Import/AssetCreation/GameAssetFactory.cs:195-205`:
  it tries the TPK type-tree blob (`TypeTreeNodeStruct.TryMakeFromTpk`), and only if that also misses
  does the asset become an `UnknownObject`
  (`Source/AssetRipper.Import/AssetCreation/GameAssetFactory.cs:147`).
- The TPK blob is embedded in the *same* 1.4.0 package (`SourceTpk`, produced by
  `Source/AssetRipper.AssemblyDumper/Passes/Pass557_CreateSourceTpkClass.cs:17-18`), so it covers the
  same version range. Its lookup,
  `Source/AssetRipper.Import/Structure/Assembly/TypeTrees/TypeTreeNodeStruct.cs:478-510`
  (`GetItemForVersion`), is also greatest-lower-bound and only throws on a malformed list, not on a
  high version.

**The real failure mode is a layout that is present but wrong**, which shows up as a byte-count
mismatch, not as an exception:
`Source/AssetRipper.Import/AssetCreation/GameAssetFactory.cs:206-209` builds
`Read {pos} but expected {len} for asset type {T}. V: {version} ...` and
`:133` logs it as an error before replacing the asset with an `UnreadableObject`.

**Verify — this is the single most important layout grep:**
```sh
grep -cE "Read [0-9]+ but expected" "$LOG"          # expect 0
grep -E "Read [0-9]+ but expected" "$LOG" | head -20
grep -c "Unreadable\|UnknownObject" "$LOG"   # NB: plain -i "unreadable" also matches
                                             # the "ExportUnreadableAssets: False" settings line
```
Any hit names the exact class whose 6000.0.66 layout is wrong. Note the retry at
`GameAssetFactory.cs:124-132` only fires for `UnityVersionType.Patch` builds; `6000.0.66**f**2` is
`Final`, so there is **no** second attempt here — the first mismatch is fatal for that asset.

## 7. Shader export at `ShaderExportMode.Decompile` — **suspect**

**No Unity-version gate in the shader path is an upper bound.** Every comparison in
`Source/AssetRipper.Export.Modules.Shaders/` is a lower bound and evaluates correctly for 6000.x:
- `Processor/ShaderSubProgram.cs:30` `version.GreaterThanOrEquals(5, 5)` → true
- `Processor/ShaderSubProgram.cs:31` `version.LessThan(2021, 2) && version.GreaterThanOrEquals(2019, 1)` → false, correct
- `Processor/ShaderSubProgram.cs:70` `version.LessThan(2021)` → false, so params come from the separate blob entry (the 2021.2+ layout) — correct for Unity 6
- `Processor/ShaderSubProgram.cs:80` `version.GreaterThanOrEquals(5, 5)` → `ShaderGpuProgramType55` — correct

**The risk is not the version, it is the platform.** `Decompile` is built around Direct3D bytecode, and
an arm64 Android build contains none.
`Source/AssetRipper.Export.UnityProjects/Shaders/ShaderDecompileExporter.cs:246-288`
(`GetPlatformIndex`) picks in this order:
1. `D3D11 / D3D11_9x / D3D9` → real HLSL. **Cannot occur in this apk.**
2. `Gles3x / Gles20 / GlCore / OpenGL` → the stored GLSL is handed back verbatim (`:88-92`).
3. `Vulkan` → SPIR-V, and only **disassembled** (`:94-98`), after a SMOL-V decode
   (`Processor/SpirvProgram.cs:25`).
4. Nothing → warns and the pass bodies come out empty (`:281-286`).

And crucially, SPIR-V assembly is written out **as a comment**, not as a program:
`Source/AssetRipper.Export.Modules.Shaders/Processor/ShaderLabWriter.cs:717`
```cs
bool comment = resolved.Program!.Value.Language == ShaderProgramLanguage.SpirvAssembly;
```

So the realistic outcomes for this game, best to worst:
- Build shipped GLES3 → shaders export with real GLSL bodies. Usable.
- Build shipped Vulkan only → **every shader exports with its program commented out**. The ShaderLab
  structure survives, the shaders do not render. This is a silent quality loss, not an error.
- Neither → one warning per shader, empty passes.

There is also an unguarded throw worth knowing about:
`Source/AssetRipper.SourceGenerated.Extensions/Enums/Shader/GpuProgramType/ShaderGpuProgramType55.cs:78`
```cs
_ => throw new Exception($"Unsupported gpu program type {_this}"),
```
The enum stops at `RayTracing = 31` (`:37`). Any program-type ordinal Unity 6 added beyond 31 throws.
That throw is caught per shader at `ShaderDecompileExporter.cs:36-40` and falls back to a dummy
shader, so it degrades rather than aborting — but it degrades **loudly**, which is the grep below.

**Verify:**
```sh
grep -n "has no program that can be recovered" "$LOG"          # names the platforms actually present
grep -n "Failed to decompile shader" "$LOG"
grep -n "Unsupported gpu program type" "$LOG"                  # enum gap -> Unity 6 added a type
ls "$OUT/Assets/Shader" 2>/dev/null | head
grep -rl "SPIR-V\|OpModule\|OpEntryPoint" "$OUT/Assets/Shader" 2>/dev/null | head   # = commented-out path
```
If the third grep hits, add the missing ordinals to `ShaderGpuProgramType55.cs`.
If shaders come out commented, `ShaderExportMode.Yaml` preserves more information than `Decompile`
does for a Vulkan-only build.

## 8-9. The `.xapk` path — **fine** (both apks merged), one latent limit

`Source/AssetRipper.Import/Structure/ZipExtractor.cs:66-84`:
```cs
private static string ExtractXapk(string xapkFilePath, FileSystem fileSystem)
{
	string intermediateDirectory = fileSystem.Directory.CreateTemporary();
	string outputDirectory = fileSystem.Directory.CreateTemporary();     // ONE directory
	DecompressZipArchive(xapkFilePath, intermediateDirectory, fileSystem);
	foreach (string filePath in fileSystem.Directory.GetFiles(intermediateDirectory))
	{
		if (GetFileExtension(filePath, fileSystem) == ApkExtension)
		{
			DecompressZipArchive(filePath, outputDirectory, fileSystem);  // same target every iteration
		}
	}
	return outputDirectory;
}
```
`outputDirectory` is created **once, outside the loop**, and every inner `.apk` is decompressed into
it. That is what merges the base apk (`assets/bin/Data/…`: `global-metadata.dat`, `data.unity3d`) with
the split config apk (`lib/arm64-v8a/libil2cpp.so`). `.xapk` reaches this branch via the switch at
`:41-45`.

**Confirmed in the log** — two different sources, one identical destination:
```
From: .../05cdcf8d/config.arm64_v8a.apk      To: .../e11fa7d6
From: .../05cdcf8d/com.b2p.gobbledash2.apk   To: .../e11fa7d6
Android game structure has been found at '.../e11fa7d6'
```

**What would have happened had they not merged — and which log line actually proves it.**
This matters, because the obvious line is the wrong one:

- `Android game structure has been found` (`Platforms/PlatformChecker.cs:150`) is **NOT** proof of the
  merge. Its condition, `AndroidGameStructure.IsAndroidStructure` (`Platforms/AndroidGameStructure.cs:69-85`),
  checks only a root-directory name score and that `assets/bin/Data` exists (`:82-84`). The **base apk
  alone** satisfies it. This line would have printed either way.
- **`Files use the 'IL2Cpp' scripting backend.` is the proof.** The two halves come from different
  apks and must land in one root (`Platforms/AndroidGameStructure.cs:23-27`):
  ```cs
  ManagedPath          = Path.Join(GameDataPath, ManagedName);          // base apk
  LibPath              = Path.Join(RootPath, LibName);                  // config.arm64_v8a apk
  Il2CppGameAssemblyPath = GetIl2CppGameAssemblyPath(LibPath);          // lib/arm64-v8a/libil2cpp.so
  Il2CppMetaDataPath   = Path.Join(ManagedPath, MetadataName, DefaultGlobalMetadataName);
  ```
  and the backend is only set to IL2Cpp when **both files exist**
  (`Platforms/PlatformGameStructure.cs:403-409`):
  ```cs
  protected bool HasIl2CppFiles() =>
      Il2CppGameAssemblyPath != null && Il2CppMetaDataPath != null &&
      FileSystem.File.Exists(Il2CppGameAssemblyPath) && FileSystem.File.Exists(Il2CppMetaDataPath);
  ```
  Had the two apks gone to separate directories, `HasIl2CppFiles()` would be false, `Backend` would
  fall through to `Mono` or `Unknown` (`AndroidGameStructure.cs:31-41`), no `IL2CppManager` would be
  constructed, and the run would export assets with **no method-body recovery at all** — while still
  printing `Android game structure has been found`. That is the silent-degradation shape to watch for.

Both lines are present in this log (L35 and L38), so the merge worked.

**Latent limit (not hit here):** `fileSystem.Directory.GetFiles(intermediateDirectory)` at `:76` is
**not recursive**. An `.xapk` that nests its apks in a subfolder would silently yield an apk-less
directory. Both of this game's apks sit at the archive root, so it is fine — but it is the first thing
to check on the next split build. Also note `WriteEntryToDirectory` uses `File.Create` (`:133`), which
**overwrites**: files present in both apks (`AndroidManifest.xml`, `resources.arsc`) end up as
whichever apk was extracted last. Neither is read by AssetRipper, so it does not matter here.

**Verify:**
```sh
grep -n "Decompressing files" -A2 "$LOG" | grep "To:" | sort -u   # expect ONE distinct destination for the two apks
grep -n "Android game structure has been found" "$LOG"
grep -n "scripting backend" "$LOG"
```

## 12. Tables that clamp to their newest entry — **suspect (silent)**

Three places degrade quietly rather than failing when the embedded data predates the game's version.
None throws; none logs. They are worth knowing about precisely because nothing tells you:

- `Source/AssetRipper.Export.UnityProjects/Scripts/AssemblyDataFile.cs:19-22` —
  `if (version >= Assemblies[^1].Key) return Assemblies[^1].Value;` The reference-assembly table
  decides which assemblies are treated as Unity's own and skipped vs. decompiled
  (`ReferenceAssemblies.cs:26`). A 6000.x game gets the newest entry in the 1.4.0 package.
- `Source/AssetRipper.Export.UnityProjects/EngineAssets/EngineAssetsExporter.cs:42-55` — same
  clamp-to-last for the engine-asset GUID table. A wrong entry means engine assets resolve to the
  wrong GUIDs (pink materials, missing default meshes).
- `Source/AssetRipper.Export.UnityProjects/Scripts/OriginalSourceSubstitution.cs:647` —
  `Enumerable.Range(6000, 20)` covers majors 6000-6019, but the inner minor loop at `:649` caps at 9,
  so no `UNITY_6000_10_OR_NEWER` symbol is emitted. Irrelevant at 6000.0.

**Verify:** these have no log line. Check the output instead:
```sh
ls "$OUT/Assets/Scripts" | head -40                # are UnityEngine.*/Unity.* assemblies decompiled?
grep -rn "guid: 0000000000000000" "$OUT/Assets" 2>/dev/null | head    # unresolved engine asset refs
```

## 13. `DefaultVersion: 0.0.0a0` — **fine for this game, but it is the one real trap in Import**

`0.0.0a0` **is** `default(UnityVersion)` — "unset", not a real version
(`Source/AssetRipper.Import/Configuration/ImportSettings.cs:35,41`; neither has an initializer).

- **`TargetVersion` unset is correct behavior.** `GameInitializer.cs:25` (`if (TargetVersion != default)`)
  skips the experimental version rewrite, and `EngineResourceInjector.cs:63-65` substitutes the real
  version. Nothing is lost.
- **`DefaultVersion` unset is a trap for version-stripped files.** The chain:
  `Source/AssetRipper.Import/Structure/GameStructure.cs:40` passes `DefaultVersion` →
  `Source/AssetRipper.Assets/Collections/SerializedAssetCollection.cs:55`
  `file.Version.Equals(0, 0, 0) ? defaultVersion : file.Version` →
  `Source/AssetRipper.Import/AssetCreation/GameAssetFactory.cs:52`
  ```cs
  if (assetInfo.Collection.Version.LessThan(3, 5))
  {
      //Assets with a stripped version can't be read.
      return new UnreadableObject(assetInfo, assetData.ToArray());
  }
  ```
  A stripped collection becomes `0.0.0a0`, which is `LessThan(3, 5)`, so **every asset in it becomes
  `UnreadableObject`** — even though `IL2CppManager` logged `6000.0.66f2` four steps earlier.

  The detected version is right there and is never offered as the fallback:
  `IL2CppManager.cs:119` sets `UnityVersion` at `GameStructure.cs:36`, one line before `:40` uses
  `DefaultVersion` instead. `IL2CppManager.UnityVersion` (`:92`) has **no consumer anywhere in the
  repo** and is not on `IAssemblyManager`.

  For this game the Android path does set a version — `AndroidGameStructure.cs:30`
  `Version = GetUnityVersionFromDataDirectory(GameDataPath)` — and `data.unity3d` reports
  6000.0.66f2, so the trap should not fire. **Confirm it did not.**

**Verify:**
```sh
grep -n "Game files have these Unity versions" "$LOG"    # 0.0.0a0 in this list == the trap fired
grep -n "Unreadable" "$LOG" | grep -v ExportUnreadableAssets
```
**Workaround if it fires:** set `DefaultVersion` to `6000.0.66f2` in the run settings.
**Fix:** at `GameStructure.cs:40`, fall back to the detected version when `DefaultVersion == default`.

## Also confirmed, outside `Source/` but decided by the Unity version

The metadata 31 → **31.1** choice is made by a Unity-version comparison, and it is correct here:
`External/Cpp2IL/LibCpp2IL/Metadata/Il2CppMetadata.cs:149-159`
```cs
else if (version == 31)
    if (unityVersion.GreaterThanOrEquals(2022, 3, 33, UnityVersionType.Final, 1))

```
6000.0.66f2 ≥ 2022.3.33f1 → `31.1`. **The log already proves this fired correctly:**
`Cpp2IL : Using actual IL2CPP Metadata version 31,1`. This is the single highest-consequence
version-dependent decision in the whole run — 31 instead of 31.1 would misparse every method
definition — and it is settled.
