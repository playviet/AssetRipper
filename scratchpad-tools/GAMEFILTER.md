# What in Snacky Dash is actually the game

`gamefilter.py` answers one question the scorers cannot: of the 167817 methods in
`com.b2p.gobbledash2`, which ones does anybody care about?

**93.1% of them are not the game's code.** Recovery effort spent there is mostly wasted, and every scorer in
`scratchpad-tools/` currently counts all 167817 equally — so a win on `System.Linq` and a win on the snake
are the same number today.

```
167817 methods in 172 assemblies

bucket        methods    share
game            11601    6.91%
sdk             54134   32.26%
unity           58205   34.68%
bcl             43877   26.15%
  gameplay       7946    4.73%
  meta           3655    2.18%
```

Naming the game's assembly is not enough. `Assembly-CSharp.dll` is 21415 methods and **10051 of them are
somebody else's** — the Voodoo publishing SDK, Easy Save 3, HighlightPlus and a consent manager compiled
straight into it. That is the single most important fact in this document: an `Assembly-CSharp`-only scorer
is still wrong by a factor of two.

## How this was measured

Two files out of the apk, no export needed. `unzip -p` them from
`com.b2p.gobbledash2.apk`, which is itself inside `Snacky Dash_1.11.0.xapk`:

| file | what it gives |
|---|---|
| `assets/bin/Data/ScriptingAssemblies.json` | all 225 assemblies Unity compiled, each tagged `2` (a UnityEngine module, 69 of them) or `16` (everything else, 156) |
| `assets/bin/Data/Managed/Metadata/global-metadata.dat` | the 172 assemblies that survived stripping, every namespace and type in each, and the method count of each type |

Getting them out, and the census, in four commands:

```sh
cd "$(mktemp -d)"
unzip -o -q "/Users/playviet/Documents/_APK/Snacky Dash/Snacky Dash_1.11.0.xapk" com.b2p.gobbledash2.apk
unzip -p com.b2p.gobbledash2.apk assets/bin/Data/ScriptingAssemblies.json > assemblies.json
unzip -o -q com.b2p.gobbledash2.apk 'assets/bin/Data/Managed/Metadata/global-metadata.dat'
python3 ~/Documents/_BZ/AssetRipper/scratchpad-tools/gamefilter.py \
    --census assets/bin/Data/Managed/Metadata/global-metadata.dat --queue
```

The metadata parse lives in `gamefilter.py` as `census()` and runs in 0.06s.

It is trustworthy because it is checkable: the per-image method counts sum to **exactly 167817**, which is
the number Cpp2IL prints as `Processed 167817 OK`. Metadata version here is 31.1, where every index is a
fixed `int32`; v38 and later use the dynamic widths in LibCpp2IL's `Il2CppVariableWidthIndex` and this
reader would need that layout.

### Nested types have to be rooted, or the numbers are wrong

A nested type carries an **empty namespace** in the metadata. Counted naively, `Assembly-CSharp`'s global
namespace looks like 4588 methods, because every `<>c` closure and every `<Foo>d__12` state machine of every
`JuicedUp` type lands there. Attributed to the type that declares them — which is where the export puts
them, since AssetRipper writes a nested type inside its parent's file — the global namespace is **1633**.
`census()` walks the `nestedTypes` table to do this.

## The rules, and where they can be wrong

`bucket()` applies four rules in order, and the ordering is the design:

1. **The assembly tables.** Exhaustive for this build — all 239 names (172 in the metadata, 225 in
   `ScriptingAssemblies.json`, union 239) are covered by a table or by rule 4.
2. **`NAMESPACE_OVERRIDES`**, for third party vendored *into* a game assembly. Without this rule
   `Assembly-CSharp` is 21415 game methods instead of 11354.
3. **`GLOBAL_TYPE_PREFIXES` / `GLOBAL_TYPE_NAMES`**, for vendored types with no namespace to be caught by.
4. **Prefix fallback**, for an assembly in no table: `System.`/`Microsoft.`/`Mono.`/`mscorlib`/`netstandard`
   → `bcl`; `UnityEngine.*`/`Unity.*` → `unity`; anything else → `sdk`.

   **An unknown assembly is never `game`.** The game's assemblies are named explicitly, so a new one is a new
   fact about the build rather than something to infer — guessing `game` would quietly inflate the one
   number this tool exists to keep honest. 98 of the 239 names reach rule 4 and every one lands right (68
   `UnityEngine.*Module` → unity, 30 `Microsoft.*`/`System.*` → bcl); nothing falls through to `sdk` by
   accident.

### Judgement calls, each a one-line edit

- **`Unity.Services.*`, `UnityEngine.Purchasing.*`, `UnityEngine.Advertisements`, `Unity.Notifications.*`,
  `Unity.Analytics.DataPrivacy` are `sdk`, not `unity`**, though Unity publishes them. The split asked for
  is by what the code *does* — analytics, IAP, ads — not by who ships it. Moving them to `unity` shifts
  3586 methods and changes no `game` number.
- **`CloudContent*` is `game`/`meta`.** It is a remote-content client: infrastructure rather than gameplay,
  but written for this title family rather than bought. 247 methods.
- **`MobileGameShop` is `game`/`meta`.** `ShopPresenter`, `UnityIapProvider`, `GrantVisualCatalogSO`,
  `PlayerPrefsEntitlementsService` read as a studio module, not an asset — but it sits beside
  `JuicedUp.Features.Shop`, which is odd. 157 methods.
- **`Newtonsoft.Json`, `UniTask`, `DOTween`, `Sirenix.*` are `sdk`.** They are third-party libraries, not
  SDKs; the four buckets have no separate slot for them, and `sdk` is the third-party bucket.

## The fix queue

`tier()` splits `game` in two. **`gameplay`** is product code — the board, the snake, the crates, the levels,
the screens a player sees. **`meta`** is the game's own plumbing — save and load, the api client, config,
notifications, the debug menu, and every `.Analytics` under a feature (a leaf-segment rule, so a feature that
grows one later is caught without an edit).

## Using it from another scorer

```python
import sys, os
sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from gamefilter import is_game_code, bucket, tier, split_path, scripts_root

root = scripts_root(export)                                  # <export>/ExportedProject/Assets/Scripts
assembly, namespace, type_name = split_path(root, path)      # from a .cs path
if is_game_code(assembly, namespace, type_name):
    ...
```

## Do not point it at another game

`bucket()` is table-driven, and the tables are Snacky Dash's. Run against Fluffy Field it reports **96.6%
game** — because rule 2 has nothing to say about another title's assets, so `CFramework`, `Dreamteck` and
`EnhancedScroller` all come out first-party. The CLI therefore refuses to report unless
`Assembly-CSharp/JuicedUp` is in the export (`MARKER` at the top of the file); `is_game_code()` itself does
not check, because a per-call check would cost more than it saves.

Another title needs its own tables, not a second copy of the logic. Regenerate them the same way: pull
`ScriptingAssemblies.json` and `global-metadata.dat` out of the apk, run `--census --queue`, and read the
namespaces per assembly. The Unity, BCL and common-SDK rows carry over unchanged; only `GAME_ASSEMBLIES`,
`NAMESPACE_OVERRIDES`, `GLOBAL_TYPE_*`, the tier lists and `MARKER` are per-title.

`--selftest` pins 34 classifications with no files and no export, so a table edit that breaks an old
decision is caught in 0.05s.
